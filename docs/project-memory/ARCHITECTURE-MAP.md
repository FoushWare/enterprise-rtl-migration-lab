## RTL review workflows — verified 2026-11-16

Both dashboard review modes use a persisted [workflow/session coordinator](../../tools/rtl-scanner/src/review-workflow.ts), the existing [codemod](../../tools/rtl-scanner/src/codemod.ts), isolated [candidate/runtime implementation](../../tools/rtl-scanner/src/review-session.ts), and [controlled apply journal/backups](../../tools/rtl-scanner/src/controlled-apply.ts). This is not universal RTL migration or arbitrary component isolation. Ahmed's personal acceptance remains unchecked.

## Automatic Before/After lifecycle — verified 2026-11-18

This supersedes earlier manual-only preparation and post-rollback “no candidate” behavior, preserving their historical decisions/evidence. The [workflow coordinator](../../tools/rtl-scanner/src/review-workflow.ts) has one serialized isolated preparation operation with current source/configuration, candidate, eligibility and route checks. The [dashboard coordinator](../../tools/rtl-scanner/src/dashboard-review-workflow.ts) starts it after verified Before, coalesces requests, ignores stale selection/descriptor responses, reuses valid sessions after reload and prepares a fresh selected patch after authorized rollback/rescan. Ready requires the actual mapped candidate target; unsupported mappings remain blockers and failures offer one Retry. Preview preparation does not approve, validate or apply to project source; fresh successors keep Pending/Not run and historical receipts/validation stay separate.

The [standalone HTTP lifecycle tests](../../tests/e2e/automatic-after.spec.ts) cover initial selection, delayed descriptor/preparation, reload/session restore, rapid switching, failure/Retry, unsupported mappings, both rollback/rescan modes and target-source hashes.
