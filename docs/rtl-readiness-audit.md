# Atlas Invoice — RTL technical readiness audit

**Audit date:** 11 October 2026. **Scope:** existing English LTR source, both applications, shared UI/data libraries, installed MUI behavior, tests and screenshot assets. **Disposition:** ready for a controlled Phase 2 proposal; not ready to declare RTL support. No application, configuration, dependency, test or baseline changes were made. Only this report was added. No Arabic content, runtime direction changes, RTL styling plugin or codemod was implemented or exercised.

## 1. Readiness assessment

The strongest migration seam is the shared Provider and AppShell: both applications already consume them. The main blockers are an immutable LTR theme, LTR document roots, no application-owned RTL Emotion cache, and shell geometry tied to the left side. Layout is split across plain CSS, Emotion templates, MUI `sx`, and React inline styles. One styling strategy cannot automatically handle all four.

There are genuine automation candidates in decorative spacing and start/end affordances. Shell placement, SVG charts, directional meaning, mixed text and field behavior require decisions before transformation. Existing LTR tests provide a useful safety net, but they do not establish RTL correctness. All future implementation recommendations below require approval first.

**Evidence boundary:** source findings are confirmed in the current files. RTL symptoms are predictions from that source and installed library behavior, not observed RTL failures. The current English application is intentionally LTR; these are migration challenges, not accusations of broken LTR behavior.

## 3. Classification rules

- **Safe automation candidates (A):** bounded syntax changes with clear reading-start/reading-end intent. This is a candidate list, not authorization to apply transformations. Preserve LTR screenshots and review output after eventual changes.
- **Requires manual review (M):** product semantics, coupled geometry, chart coordinates, glyphs, content direction or reading/interaction order. A textual match is insufficient to choose the final behavior.
- **Requires runtime RTL configuration (R):** document direction, MUI direction context, Emotion processing, portal inheritance and locale-dependent rendering. Static property replacement cannot supply these.

Classifications describe the primary treatment. Some manual findings also depend on runtime configuration. Symmetric padding, gaps, centered content and vertical spacing are not automatically RTL defects.

### 4.5 Bidirectional content and formatting

**Classification: M for isolation/content policy; R for locale-aware formatting.** Source searches found no `bdi`, application `dir=auto`, token-specific `dir=ltr` or `unicode-bidi` rules. HTML roots are the only explicit direction attributes. Do not assume RTL text reverses every Latin token: many complete Latin identifiers already form an LTR run. Risks depend on mixed surrounding text, punctuation, numeric runs and user-entered content; they require targeted future examples. The [W3C inline bidi guidance](https://www.w3.org/International/articles/inline-bidi-markup/) supports wrapping known opposite-direction phrases and isolating content whose direction is not known in advance.
